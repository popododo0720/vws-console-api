# Rules: full statements

`AGENTS.md` lists every rule in one line with its main check. This file has
the full statement of each rule and every test, lint or CI job that enforces
it. When you add or change a rule, change its row here and its line in
`AGENTS.md` in the same pull request, and add its check.

| Over gRPC with `-launch-namespace`, `RunInstances` keeps one launch record per client token: a ConfigMap `launch-<key>` in that namespace, labeled `app.kubernetes.io/managed-by: vws-console-api` and `vws-launch-phase: <phase>`, keyed by the idempotency key (account, action and client token), so the token itself is never stored. The record holds the account, the request fingerprint, the count, the phase (`running`, `undoing`, `failed`, `succeeded`), the attempt, the plan and each completed boot volume and instance create of the attempt, in order, by backend resource name. The plan names every volume and instance the attempt may create; their ids are derived from the key and the attempt, so it is written once per attempt and a create whose step write failed or never ran is still named. It is created after every check that refuses a launch and before the first create, so a launch refused before its first create writes nothing and a launch whose record cannot be written creates nothing. A refusal from a create, such as an unsupported volume type, is recorded `failed`. It is written only on a transition, under the vws-deploy#478 rules: a new step, a phase change, or the launch GC collecting an attempt. A retry that changes nothing writes nothing, and `succeeded` is final. Every write is a compare-and-swap on `resourceVersion`, so a no-op retry leaves `resourceVersion` unchanged; a conflict reloads and applies the change again, so two requests with one token both land their steps. A token reused with another fingerprint or count is `IdempotentParameterMismatch` before any create. A failed record write is `Unavailable`, and a retry with the same token resumes the launch, because every volume and instance id is derived from the key. A retry of a failed launch is a new attempt with its own plan and no steps, and only the latest attempt may undo the launch, so a stale request never fails a retry. A completed step and the launch's end are written past a cancelled request, within 10 seconds each. The whole ConfigMap, with 16 KiB kept for the metadata the API server adds, stays under the vws-deploy#478 256 KiB object limit, and a larger one is refused before it is sent; the largest launch, 10 instances, is under 5 KiB. One HTTP request to the Kubernetes API times out after 3 seconds. One store call is tried at most 4 times, with backoff from 50 ms, on a request timeout, 429, 500 or 503, and ends within 10 seconds with every retry included, client-go's own `Retry-After` retries too; a conflict, a missing object or an expired caller deadline returns at once. Without `-launch-namespace` nothing is recorded and the process logs a warning; with it, `-kubeconfig` names the cluster, and when empty `$KUBECONFIG`, then the default kubeconfig path, then the in-cluster service account; a kubeconfig that cannot be loaded stops startup, and so does `-launch-namespace` with `-backend=fake`. The client sends at most 50 requests a second, bursts of 100. The service account needs only `get`, `list`, `create` and `update` on `configmaps` in that namespace, as a namespaced Role. `Update` rewrites the whole ConfigMap, so a label or annotation added by hand is dropped on the next write. In CI the envtest tests fail instead of skipping when `KUBEBUILDER_ASSETS` is unset. | Over gRPC with `-launch-namespace`, a `RunInstances` step that fails (a create, the instance read after it, or the record write of a step) undoes the attempt before the error returns. The record moves `running` to `undoing` before the first delete, so a request that resumes the attempt never uses a deleted resource; then every resource of the attempt's plan is deleted, last step first: an instance, which takes its boot volume and private IP with it, then a boot volume whose instance was never made. A delete of a missing resource succeeds, so the plan covers a create whose step was never recorded. Each delete is waited on, tried at most 3 times with backoff from 100 ms on `Unavailable`, and the whole undo ends within 2 minutes, past a cancelled request. When every delete is done the record is `failed`. A retry with the same token after that is the next attempt, with ids derived from the key and that attempt, because a backend replays a reused request id with the deleted resource. An undo cut short stays `undoing`, and the next request with the token finishes it before it launches. An undo the record cannot hold deletes nothing and leaves the launch `running`, so the retry resumes the same attempt. A request of an attempt that another request began to undo, or that a later attempt replaced, cannot record a step or succeed: it is `Unavailable`, and its retry returns the current attempt. When its step lands after the undo began, in that attempt, it runs the undo again, so the create it made late is deleted; a create that lands after a later attempt began is deleted by the launch GC. Without `-launch-namespace` nothing is undone. | `TestFailureAtEveryStepIsUndone`, `TestUndoDeletesInReverseOrder`, `TestCutShortUndoIsFinishedByTheRetry`, `TestUndoNeedsTheRecord`, `TestCreateAfterAnUndoIsUndone`, `TestRunInstancesFailureRecordsCompletedSteps`, `TestSuccessAfterAnUndoIsRefused`, `TestStaleAttemptCannotFailARetry` |
| Over gRPC with `-launch-namespace`, a `RunInstances` launch whose process died (killed between two calls) is resumed or undone. A retry with the same token before the sweep resumes the attempt, because every id and request id is derived from the key and the attempt. Otherwise the launch sweep undoes it. Each process sweeps once at start and then every minute: it lists the records whose `vws-launch-phase` label is neither `succeeded` nor `failed` (a record without the label is listed too), a page of 250 at a time, and undoes every launch left `running` or `undoing` whose record was last written 10 minutes or more ago, as its latest attempt, by the same undo a failed step runs, 20 launches at once. The sweep claims a launch only while its record is still that idle, after any reload on a conflict, so a launch a retry wrote after the listing is left alone. A request writes its record on every new step, and its longest gap between writes is about 70 seconds (two 30-second calls and a write), or about 2 minutes 10 seconds in an undo. A retry that replays steps already recorded writes nothing until a new step, so a replay that runs past the 10 minutes, or a sweeper whose clock runs ahead of the writer's, can sweep a live launch. That is still safe: once the record says `undoing`, the live request cannot record a step or succeed, it undoes its own late creates and answers `Unavailable`, and the next retry is the next attempt. A launch whose process died is undone within 10 minutes idle, up to 1 minute until the next sweep, and 2 minutes 10 seconds for each round of 20 launches that sweep undoes, while the services answer: 13 minutes 10 seconds for up to 20 launches, and 21 minutes 50 seconds for one process that died at its in-flight cap of 100. An undo cut short stays `undoing` and the next sweep finishes it. Every replica sweeps; two sweeps of one launch serialize on the record's compare-and-swap and send the same delete request ids. A retry with the same token after the sweep is the next attempt, and a second retry returns the same instances. A record that cannot be decoded does not stop the sweep of the others; the sweep reports it. A failed sweep is reported through `report.Error` naming the launch key and the error code only, never a backend message, which names the account's resources; a sweep that undid launches logs how many. The sweep does not run without `-launch-namespace`. At shutdown it starts no further undo; one in progress may be cut short and is finished by the next sweep of any process. | `TestCrashAfterEveryStepIsResumedOrSwept`, `TestOneSweepUndoesMoreLaunchesThanItRunsAtOnce`, `TestAbandonedIsAnIdleRunningOrUndoingLaunch`, `TestAbandonedLaunchIsUndoneOnce`, `TestAbandonedLaunchWrittenSinceIsLeftAlone`, `TestUnfinishedReadsEveryOpenRecordAcrossPages` |
| Over gRPC with `-launch-namespace`, the launch GC deletes what a dead attempt left (#392). An attempt is dead once it can create nothing more: every attempt before a launch's latest one, and the latest one once it is `failed`. A running, undoing or succeeded attempt is never dead, and an attempt once dead stays dead, because a retry of a failed launch is the next attempt. A create can land after its attempt was undone, by a request that a retry replaced or one the backend applied after its request gave up; the undo of that attempt never sees it. The GC runs in the launch sweep, after its undo pass, at start and then every minute. It lists the records whose `vws-launch-gc` label is `pending`, and the `failed` records written before the label existed, a page of 250 at a time; every write labels a record `pending` while a dead attempt is left uncollected and `done` after. A succeeded record written before the label is not listed, so a create left by an earlier attempt of such a launch is not collected; an open one gets the label on its next write. It collects only a `failed` or `succeeded` launch whose record was last written 10 minutes or more ago, and never lists a `running` or `undoing` one; a launch the sweep fails is collected 10 minutes after that. A retry that moves a listed launch back to `running` during a pass does not stop the pass: it deletes only attempts that were already dead, whose ids are not the running attempt's, so no resource of a running, undoing or succeeded attempt is ever deleted. For each dead attempt not yet collected, in order, it deletes every volume and instance of the attempt's plan, last step first, with ids derived from the key and the attempt and delete request ids of their own, by the same waited, retried delete the undo runs; a delete of a missing resource succeeds. The succeeded attempt's ids differ from every earlier attempt's, so they are never named. Then it records `collected` for that attempt by compare-and-swap; a repeat writes nothing, and a record whose count RunInstances never accepts (outside 1 to 10) is reported and names nothing. 20 launches at once, each within 2 minutes a pass; one cut short, or whose record cannot be written, is collected again by the next pass, attempts already recorded skipped. So a late create is deleted within 10 minutes of its launch's last record write, up to 1 minute until the next pass, and 2 minutes for each round of 20 launches that pass collects, while the services answer. An attempt is collected once: a create the backend applies after its attempt was collected is not seen again. A failed pass is reported through `report.Error` naming the launch key and the error code only; a pass that collected launches logs how many. Without `-launch-namespace` nothing is collected. | `TestGCRemovesALateCreateOfAFailedLaunch`, `TestGCKeepsTheSucceededAttempt`, `TestGCNeverTouchesARunningLaunch`, `TestGCCutShortIsFinishedByTheNextPass`, `TestRetryAfterTheGCListedALaunchKeepsTheRunningAttempt`, `TestDeadIsEveryAttemptThatCanCreateNothing`, `TestCollectableIsAnIdleEndedLaunchWithADeadAttempt`, `TestCollectedIsWrittenOnceAndNeverPastDead`, `TestCollectableRefusesARecordWhoseCountItCannotTrust`, `TestUncollectedListsRecordsWithADeadAttempt` |
| `TerminateInstances` releases what an instance holds in dependency order (#392). For every instance of the request it first clears each Elastic IP association that names the instance, in spec or status, as EC2 disassociates on terminate; the address stays allocated. ## Adding a long-running action (moved from AGENTS.md)

1. Add the `Action` constant in `internal/resource`, plus its request type
   (`Action` and `Normalize`) and any lifecycle row. `exhaustive` flags a
   switch that misses it. `Actions()` is derived from the constants.
2. Add the method on the backend interface. The fake and the gRPC client stop
   compiling until they implement it.
3. Add the case to `backendtest`.
4. Add a one-line kernel method that calls `mutate`.
5. Add the console route in `handler.mutation`. `TestEveryActionHasARoute` fails until the route is real.
6. Add the query action in `ec2query` when the query protocol has that action.
7. Add an interop test when a second surface can perform the same mutation.


## e2e (moved from AGENTS.md)

`e2e/e2e.py` drives the EC2 Query and S3 entry points with boto3.
`VWS_E2E_BACKEND` is `fake` or `grpc`. `VWS_E2E_CAPS` lists what the backend
can do (`vm`, `eip`, `direct` when `VWS_E2E_DIRECT_SUBNET`, default
`subnet-direct-prod`, is a configured direct network). `VWS_E2E_ACCESS_KEY` and `VWS_E2E_SECRET_KEY` are the
root credentials the SigV4 clients sign with; they default to the public
development values, which a grpc backend refuses, so a live run sets both. A
step that needs a missing capability prints `skipped(reason)` and does not
count as a pass. The run ends with a banner that lists every skip and
`status=PASS|FAIL|INCOMPLETE`. `VWS_E2E_STRICT=1` makes a skip exit 3. CI sets
it, so the fake run cannot lose a step silently.

`cli_identity()` drives the IAM and STS actions through the aws CLI v2 the same
way, and `cli_detach()` drives `aws ec2 detach-volume` (#210). They run `VWS_E2E_AWS_CLI`, or the `aws` on `PATH`, with no profile and no
retries; without one their steps are `skipped(aws-cli not available on this
host)`, so CI, where the runner image has the CLI, fails rather than skips.

```sh
pip install -r e2e/requirements.txt
e2e/run.sh                          # fake backend, started by the script
VWS_E2E_BACKEND=grpc VWS_E2E_CAPS=vm,eip \
  VWS_E2E_ACCESS_KEY="$VWS_ACCESS_KEY" VWS_E2E_SECRET_KEY="$VWS_SECRET_KEY" \
  python3 e2e/e2e.py                # services already running
e2e/local.sh                        # grpc stack kept up for manual runs (needs VWS_E2E_BIN, VWS_E2E_IMAGES)
```

## pstack (moved from AGENTS.md)

Use these three skills, in this order, when the change adds a package, a type
other packages use, a surface, or a backend method.

1. **architect**. Sketch the caller's usage first, then the types and
   signatures. Do not start from a wire format and grow a second vocabulary.
2. **interrogate**. Put the sketch or the diff in front of more than one
   reviewer before treating it as done. Act on findings that break
   correctness, tenancy, or the single resource model.
3. **correct**. When a review catches a mistake a later agent would copy,
   make that mistake fail a compile, a lint, or a test. Update the rule
   table in the same change. Do not leave the rule as prose alone.
